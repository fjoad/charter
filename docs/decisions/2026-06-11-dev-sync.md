# dev-sync: install staleness fixed structurally

**Date:** 2026-06-11
**Status:** Accepted

## Context

The installed Charter plugin was observed badly stale twice in one development arc (v0.1.0 installed while source was v0.3.0; then v0.3.0 installed while source was v0.6.0). Stale installs were the root cause behind sibling sessions reinventing features Charter already shipped — `/charter-help` (v0.6.0) fixed discoverability *within* a version, but a stale version has stale help.

The insight: for a solo dev who hacks on the plugin daily, staleness isn't an accident — it's a structural consequence of the finish ritual, which ships releases but never refreshes the dev's own install.

## Decision

Three pieces, all using only supported Claude Code CLI surface:

1. **`scripts/dev-sync.sh`** — wraps `claude plugin marketplace update` + `claude plugin update` with a pushed-state check first (the marketplace pulls from GitHub, so syncing unpushed work would be a silent no-op). Hand-editing `~/.claude/plugins` internal state remains forbidden.
2. **Finish-ritual step** in Charter's own `workflow.md`: after pushing a release tag, run dev-sync. The ritual that caused the staleness now cures it. (Charter's own rules only — user projects don't develop Charter, so the template is untouched.)
3. **Opt-in staleness nudge in the session-start hook:** `CHARTER_DEV_SOURCE` env var or `~/.config/charter/dev-source` file pointing at the source repo. The hook compares installed vs source `plugin.json` versions; one orient line when they differ, nothing otherwise. Fail-silent on any error (bad path, missing file). This catches the forgot-to-sync case from *any* project's session.

## Alternatives Considered

1. **Hook auto-runs dev-sync when stale.** Rejected — hooks must never mutate plugin state; surprising, racy with running sessions, and an update mid-session wouldn't load anyway (restart required).
2. **Network check against GitHub in the hook.** Rejected — slow (5s hook timeout), flaky, and the local source repo IS the freshest truth for a dev.
3. **Auto-detect the source repo (no config).** Rejected — guessing paths is fragile; one-line opt-in config is honest about being a dev-mode feature. Normal users never see any of this.

## Consequences

- After every release the dev's install refreshes as part of the ritual; the perpetual-staleness loop is closed at the source.
- Sessions in other projects warn within one line when the install lags the source — the early-warning the v0.3.0/v0.6.0 incidents lacked.
- The nudge depends on the config file being set up once per machine (documented in AGENTS.md § Iterating).
- If the falsifiable claim in the v0.6.0 ADR holds (reinventions were caused by staleness + discoverability), sibling-session rebuilds should now stop entirely.
